# Final Score, Map-Context, and Product-Intuitiveness Pass — Visual & Usability Review

Companion to [health-equity-product-consolidation.md](./health-equity-product-consolidation.md) (prior pass)
and [docs/methods/screening-score-interpretation.md](../methods/screening-score-interpretation.md) (the
required scientific trace of the score, written before it was elevated visually). This document records
what changed in this pass, what independent blind usability review found, and what was fixed as a result.

## 1. What this pass changed, in one paragraph

The 0-100 composite score — traced, bounded, and documented in the methods doc — is now the product's single
objective headline number, rendered everywhere through one shared component (`packages/ui/src/
ScreeningScore.tsx`) instead of five independent, inconsistently-rounded formatting call sites. The map
gained real geographic context (a free, keyless OpenStreetMap-derived basemap with city/road/water labels,
inserted below the choropleth so labels are never covered) where previously it rendered on a completely
blank background. Hover now updates a sidebar "Quick preview" while nothing is selected, keeping the map
fully unobscured, and switches to a small non-blocking map callout once a tract is selected so the sidebar's
open profile is never erased by hovering a neighbor. The top-3 driving factors gained a visual percentile
track matching the domain rows. None of this touched scenario weights, internal scenario IDs, or the score
formula itself.

## 3. City-label and map-context behavior

**Root cause found before implementing anything**: the map had no basemap at all — `style: { version: 8,
sources: {}, layers: [{id: "bg", type: "background", ...}] }`. This is more severe than the task's assumed
starting point ("labels exist but are hidden beneath the fill"); there were no labels, roads, or water to
hide in the first place.

**Solution implemented (Option A/B hybrid, per the task's own preference order)**: added OpenFreeMap's free,
keyless, OSM-derived "positron" vector style (`https://tiles.openfreemap.org/styles/positron`) as the
basemap, then inserted every tract layer (`fill`, `no-data-hatch`, `outline`) with `beforeId` set to the
basemap's first symbol layer (`waterway_line_label`) so all 19 of the basemap's label layers — including
`label_city`/`label_town` (min-zoom 3–9, OpenMapTiles' own population/importance-ranked place layer) —
render above the choropleth. A dedicated custom label layer sourced from `geo.places` (real TIGER place
centroids, already in the warehouse) was evaluated but judged unnecessary once the basemap's own city labels
were verified live to already include all 11 target cities correctly prioritized (San Jose ranks first by
real land area in the warehouse's own `geo.places.area_land_sqm`, confirming the basemap's own OSM-based
importance ranking agrees with locally-held data). The selected-tract outline (`SELECTED_LAYER`) and the
selected-place dashed boundary are deliberately appended **without** `beforeId`, staying above every label,
so they remain visible even where a city/road label sits over the same tract.

**Attribution**: `AttributionControl({ compact: true })` — MapLibre auto-collects "OpenFreeMap © OpenMapTiles
Data from OpenStreetMap" from the tile source's own metadata. An earlier attempt to also hand-write a custom
attribution string produced a visible duplicate credit line; removed once the auto-collected one was
confirmed sufficient on its own.

**A real, non-cosmetic bug found and fixed during implementation**: under React Strict Mode's dev-only
double mount/cleanup/mount cycle, listening only for MapLibre's `load` event to set `mapReady` never fired
for a *remote* style URL — the map still rendered tiles correctly, but `mapReady` silently stayed `false`
forever, so the tract choropleth layer was never added. Fixed by also listening for `idle` and checking
`isStyleLoaded()` synchronously as two additional, redundant readiness signals.

**City-label acceptance criteria, verified live**: at county zoom, San Jose, Gilroy, Santa Cruz, Watsonville,
Hollister, and Fremont are all labeled; at closer zoom (Sunnyvale/Cupertino level), more cities appear
(Milpitas, Campbell, Saratoga, Los Gatos); at close, single-tract zoom, road names and a neighborhood label
appear instead, with the selection outline remaining visually distinct throughout.

## 4. Hover/selection interaction model — evaluated and chosen

Per the task's request to evaluate at least three alternatives, not just keep the existing implementation:

1. **Sidebar-docked hover preview** (chosen for the no-selection state): the map stays completely
   unobscured; a "Quick preview" panel in the sidebar updates on hover, showing name, the canonical score
   (compact `ScreeningScore`), top-2 domains, and a confidence flag when coverage is thin.
2. **Collision-aware floating inspector** (the prior pass's design): kept, but only for the *selected* state,
   and shrunk substantially (240px → 180px, dropped the "top domains" and "select for full profile" lines)
   since with a profile already open in the sidebar, a hovered neighbor only needs a name and a concern
   indicator, not a repeat of the sidebar's own job.
3. **Tiny polygon callout plus sidebar preview** (the actual hybrid implemented): no-selection state uses
   alternative 1; selected state uses a shrunk version of alternative 2 (`TinyHoverCallout`) so hovering a
   different tract never erases the open profile.

Verified live: hovering a tract with nothing selected updates only the sidebar, leaving the map's colors and
labels fully visible with no floating card. Selecting a tract and then hovering a *different* tract keeps
the sidebar's open profile intact and shows only a small map-anchored callout for the hovered tract.

## 5. Score consistency audit

Traced in [screening-score-interpretation.md](../methods/screening-score-interpretation.md); before this
pass, the same underlying float was rounded to the nearest integer in Explore, one decimal in Prioritize, and
two decimals in CSV exports, and the tract-detail "percentile" was actually a Monte Carlo median-rank
transform rather than a percentile of the score itself (already correctly resolved in an earlier pass by
removing the competing map-side number, and reaffirmed here as the one canonical comparison statistic).
This pass centralizes every human-facing rendering through `ScreeningScore`/`formatScreeningScore`
(`packages/ui/src/ScreeningScore.tsx`) in: Explore's headline, mobile collapsed bar, map hover/selection
callouts, Prioritize's table and CSV-adjacent decision-memo preview, Explore's tract-to-tract comparison
panel, and Advocate's server-side evidence label (`apps/api/.../services/advocacy_evidence.py`, updated to
round to the same integer convention and use the same "Health equity screening score" label text). Raw,
higher-precision values remain available in the CSV export and the "How this was calculated" disclosure,
explicitly labeled as secondary/technical, never presented as a second competing headline number.

**Prioritize's "Rank" column bug, found during the scientific trace, fixed**: the column previously used
TanStack Table's `row.index`, which is fixed to the array's original (score-sorted) position and does not
reflect a re-sort — functioning correctly by construction (since "rank" means score-rank, not "position in
whatever the table happens to be sorted by right now") but was undocumented and easy to misread as a live
position. Relabeled `Score rank` with an inline comment explaining the fixed, score-based meaning.

## 6. Blind usability review — three independent reviewers, real findings acted on

Per the task's explicit instruction not to treat approval as evidence, three cold subagent reviewers were
each given only screenshots, a one-sentence product purpose, and a fixed question list — no implementation
explanation. Reviewer 1 covered desktop Explore, Reviewer 2 covered mobile Explore, Reviewer 3 covered
Prioritize and the county-comparison sentence.

**Two findings independently corroborated by more than one reviewer, both fixed**:

1. **A genuine internal-consistency bug** (Reviewer 3, unprompted): three tracts in the Prioritize table all
   displayed `75/100` but two read "High concern" while one read "Moderate-to-high concern." Root cause: the
   concern band was computed from the *raw* unrounded score while the displayed number was rounded, so a raw
   74.6 (displays as "75") could fall on the wrong side of the 75.0 band threshold from a raw 75.4 (also
   displays as "75"). Fixed by computing the band from `Math.round(score)` — the same value shown — in both
   the visual band and the accessible name, inside the one shared `ScreeningScore` component, so the fix
   applies everywhere at once. Verified live: rows #6/#7/#8 now all read "75/100 · High concern" consistently.
2. **Confusing ceiling phrasing** (Reviewers 1 and 2, independently): "Higher screening concern than 100% of
   408 Santa Clara County tracts" reads as a literal claim of being higher-concern than every tract
   *including itself*, especially confusing next to a tie for rank #1 in the Prioritize table. The underlying
   statistic (Monte Carlo median-rank percentile) is legitimate and unchanged; only the sentence at the ≥99%
   boundary changes, to "Among the highest screening concern of any tract in the county, out of 408 Santa
   Clara County tracts."

**One additional fix from a single reviewer's specific, concrete point** (Reviewer 3): the 0–100 direction
("higher = more concern") was stated on the Explore tract-detail page but never on the Prioritize table where
the score first appears as a sortable column. Added a one-line restatement directly under the Prioritize
results summary.

**Findings disclosed as known limitations, not fixed this pass** (single-reviewer, lower-severity, or
requiring larger redesign — see §7).

## 7. Known limitations

- The five domain percentile bars (`PercentileBar`) have no visible numeric scale or endpoint labels beyond
  the text sentence beneath them (Reviewer 1). The text sentence already states direction and relative
  position in words; adding numeric tick labels to the bar itself was judged a larger visual-design change
  than this pass's time budget supports.
- On mobile, the map is almost entirely covered by the expanded bottom sheet, so the selected tract's city
  is not nameable from the sheet view alone (Reviewer 2) — an inherent tradeoff of the two-state mobile sheet
  pattern validated in an earlier pass, not newly introduced here.
- A floating circular "N" button in the bottom-left corner of every screenshot (an unrelated, pre-existing
  UI element, not part of this pass's scope) partially overlaps map/table content at some scroll positions
  on mobile, per both Reviewer 1 and Reviewer 2. Not investigated or changed, since it predates and is
  unrelated to the score/map/hover work in scope here.
- "Data coverage" and "Stability" column headers in Prioritize have no inline tooltip explaining them
  (Reviewer 3) — both concepts are explained in Validate's methods panel and in the tract-detail confidence
  section, but not inline in the table itself.
- Rank numbers in Prioritize remain strict ordinals even when scores tie (e.g., #1 and #2 both at 77) —
  disclosed in the methods doc §10 as a pre-existing, cross-cutting tie-break inconsistency in the backend
  (three different tie-break rules across different API routes), not something this UX-focused pass changed.
- No dedicated screenshot exists for a full side-by-side tract Compare view or backend-waking/unavailable
  states in the permanent screenshot set for this specific pass (a live-interaction screenshot of Compare was
  captured and inspected directly instead, per §2; those states are covered by existing Playwright
  assertions rather than static screenshots, consistent with the prior pass's approach).
