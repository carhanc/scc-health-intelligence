Companion to `docs/design/explore-health-equity-research.md` (the research/plan) and `docs/design/health-equity-ux-visual-review.md` (the first UX-redesign pass's own review, same methodology, kept separate rather than merged since it covers different pages/states). This document records the real verification evidence for this second, focused pass — generated and inspected this session, not assumed from the plan.

## 1. How this was produced

Screenshots were generated by `apps/web/e2e/visual-review-screenshots.spec.ts` (extended this pass to open the mobile bottom sheet before capturing `explore-tract-detail` below the 1280px xl breakpoint, so the screenshot shows the actual profile rather than just the collapsed summary bar) — a real Playwright spec against a live `pnpm dev` instance, not a mockup. All 10 page/state combinations × 6 breakpoints (60 screenshots) were regenerated and a representative subset individually opened and inspected this session; three new files are committed as concrete evidence (`docs/design/screenshots/`, `.gitignore`d otherwise), alongside the four already committed from the first pass.

Beyond the screenshot spec, this pass's verification also used live interactive browser sessions (both the in-app preview pane and, for cases where that tool proved unreliable — see §6 — standalone real-Chromium Playwright sessions) to exercise map-layer switching, the mobile bottom sheet's open/close/keyboard behavior, and backend-unavailable states directly.

## 3. Map layer verification

All 7 layers (`Overall screening concern`, `Health burden`, `Access barriers`, `Environmental burden`, `Resource accessibility`, `Workforce shortage`, `Data confidence`) were exercised live via the `<select>` control:

- Switching layers correctly updates the legend title, description text, the "Viewing the {layer} layer..." note, and the map's `aria-label`.
- **Zero additional network requests**: verified directly by reading the browser's network log before and after three consecutive layer switches (workforce_shortage → health_burden → confidence) — the boundaries-fetch request count did not increase (confirmed via `read_network_requests`, DEC-073's scenario-independent-domain-scores design working as intended: the map already has every layer's data from the one boundaries fetch it always makes).
- The "Data confidence" layer's legend correctly reads "Lower confidence / Higher confidence" (magnitude words describing the raw value), not an inverted "higher-is-better" phrasing — this specific case is also covered by an automated regression test (`explore-layers.test.ts`) after a real inversion bug was caught and fixed during this pass's own test-writing (see DECISIONS.md).

## 5. A genuine defect found and fixed during verification

Testing the mobile "Compare" flow live surfaced a real bug: tapping "Compare" from inside the expanded mobile bottom sheet updated the URL (`compare=1`) but left the sheet open. Since `ComparisonPanel` renders as a page-level sibling of the sheet (not inside its `<dialog>`), the newly-rendered comparison workflow was completely covered by the still-open modal's backdrop and genuinely unreachable — confirmed both by DOM inspection (`getBoundingClientRect()` showing the panel positioned correctly but visually behind the modal) and a full-page screenshot showing only the modal.

**Fixed** by closing the sheet before delegating to the parent's `onCompare` callback, matching the same pattern already used for `onSelect`/`onClearSelection` (`apps/web/app/explore/geography-detail.tsx`, `MobileSelectedSheet`). Verified fixed via the same live reproduction steps, and `responsive.spec.ts`'s "Tract detail, comparison, and evidence drawer remain operable" test was extended to open the mobile sheet and complete the Compare flow at every sub-1280px breakpoint.

A second, smaller defect was found and fixed the same way: the mobile collapsed summary bar showed a place's raw GEOID (e.g. "0668000") instead of its resolved name ("San Jose city") for place/district selections reached via a bookmarked/shared URL — a regression against the platform's own pre-existing "never show a raw place GEOID" rule (Phase 6.5), which the desktop panel already respects via the fetched profile's `name_long`. Fixed by resolving the same fetched name in `MobileCollapsedSummary` (reusing the same cached `place-profile`/`district-profile` queries `PlaceDetail`/`DistrictDetail` already make, so this costs no extra request).

## 6. A tooling artifact investigated and ruled out (not a real defect)

While verifying the backend-unavailable error state, the in-app preview-pane browser tool repeatedly showed a completely empty third column (no loading skeleton, no error card, zero console output) when the backend was stopped — initially indistinguishable from a real defect. Cross-checked with a standalone, independent real-Chromium Playwright script (not the preview pane) against the identical backend-down state: the error card (`GeographyLoadError`: "We couldn't load this place" / "Is the API running?" / Retry / Clear selection) rendered correctly and immediately. This is now also covered by a permanent, repeatable automated test (`explore-errors-and-comparison.spec.ts`, "a fully unreachable backend produces the same visible, recoverable error", using Playwright's `page.route(...).abort()` rather than physically stopping the shared dev server) — passing. The preview-pane behavior is recorded here as an investigated-and-ruled-out tooling artifact, not a product defect.

A separate, self-inflicted environment issue surfaced during the same investigation: restarting the backend server from the wrong working directory caused `.env.local`'s relative `SCC_HEALTH_WAREHOUSE_PATH` to resolve incorrectly, silently (and correctly, per the app's own truthful-fallback design) falling back to the demo warehouse, which lacks Phase-4 analytics tables — producing real, temporary 503s on analytics endpoints. This was diagnosed via the backend's own `/api/v1/warehouse-status` endpoint, fixed by restarting from the repository root, and reconfirmed via `warehouse-status` reporting `"data_mode":"live"` and the previously-503ing endpoints returning 200. Not a code defect (the fallback behaved exactly as designed and disclosed which mode was active); recorded here because it explains an otherwise-confusing stretch of transient Playwright failures during this session that were re-run and confirmed passing once the environment was corrected.

## 7. Missing-data (null-score) state

Current live data has complete score coverage (no tract currently has a null combined score), so `explore-data-integrity.spec.ts`'s live-data test honestly self-skips rather than fabricating a scenario. The null-score-never-renders-as-zero contract, and this pass's new metric-level "Insufficient data" disclosure (a domain that itself scores but is missing one of its constituent metrics), are both covered instead by controlled-fixture unit tests in `apps/web/test/geography-detail.test.tsx` — the same pattern the first UX pass already established for this exact situation.

## 8. Bundle-size / performance impact

- Zero new runtime dependencies added this pass (`apps/web/app/explore/layers.ts` and `apps/web/lib/use-media-query.ts` are both new files but contain no new imports beyond what's already in the dependency graph).
- Production build (`next build`) succeeds cleanly; `.next/static` totals ~2.6MB, consistent with the first pass's own measurements (the largest single chunk, ~1MB, is MapLibre GL, unchanged).
- Map layer switching costs zero additional network requests (§3) and recomputes only a `Map` keyed by GEOID from data already in memory (`layerRanking`, a `useMemo` scoped to `[boundariesQuery.data, layerDef]`), not a per-hover or per-frame recomputation.
- `MobileCollapsedSummary` and the expanded sheet's `SelectedGeographyDetail` deliberately share TanStack Query cache keys (`explain-score`, `tract-boundaries`, `place-profile`, `district-profile`) so mounting both (native `<dialog>` always mounts its children) never doubles network traffic.

## 9. Known limitations carried forward

- The mobile bottom sheet is deliberately 2-state (collapsed / expanded), not 3-state with an intermediate drag-resizable height — judged, given this pass's scope, a materially larger engineering effort (drag physics, snap points, a keyboard/screen-reader equivalent for the drag gesture) than the two-state sheet, which already satisfies the collapsed-content and non-broken-focus-trap requirements. Recorded as a disclosed scope decision, not a silent omission (see `MobileSelectedSheet`'s own doc comment in `geography-detail.tsx`).
- The "Strong driver" vs. "Contributor" badge threshold (1.5× the mean metric contribution) is a documented, disclosed display threshold (DEC-074), not a new scoring methodology — it changes no underlying score, weight, or rank, only which metrics get a visual emphasis badge in the driver list.
- Full 60-screenshot visual review was inspected via a representative subset (three newly curated captures spanning the orientation panel, desktop profile, and mobile expanded sheet), not all 60 individually — the automated suites (§4) catch structural/functional regressions across every breakpoint; the manual pass exists specifically for genuine visual judgment, which does not require re-deriving the same judgment 60 times once a representative sample shows no defect pattern.
